## 3. Канон шести противников «Муравьиной революции»

Опубликованы: `red-infantry` (красная пехота), `cordyceps` (независимая грибная угроза всем колониям), `red-titan` (муравей-исполин), `bombardier` (жук-бомбардир), `burrow-worm` (норный червь), `worm-handler` (его погонщик). **Червь и погонщик — разные существа.** Норный червь занимает **3×1 клетки**, исполин **2×2**; остальные 1×1. Это габариты для БУДУЩЕЙ тактической карты; полноценная карта с проверкой занятых клеток пока не готова.

Сведения о действующих статах, балансировке и способностях брать **только** из `bestiary-data.js` + `public.bestiary_templates`; не придумывать новый канон. Особые эффекты могут ещё требовать ручного ведения ГМом.

**Ключевая механика:** муравьи живут сегментами здоровья. При потере бойца максимум ОЗ уменьшается. Обычное лечение восстанавливает ОЗ только выживших; при `7/8 +3` получается `8/8`, не `16/16`; при `0` отряд не воскрешают лечением. Долгий отдых с разрешения ГМа может пополнить живой отряд из тыла. Исключение ГМа для полной численности отделено от обычного лечения.

Навигация между листами учитывает поиск и фракцию из каталога (q и faction в URL). Предыдущий лист — толстая стрелка слева, следующий — справа. У первого/последнего только существующий сосед; при одном результате переходов нет. Возврат в каталог восстанавливает фильтры.

## 5. Supabase: реальные таблицы и безопасность

При предыдущей проверке `public` содержал: `profiles`, `characters`, `room_templates`, `rooms`, `room_members`, `room_units`, `room_events`, `room_requests`, `bestiary_templates`. Включена RLS. Обязательны серверная проверка прав и атомарные изменения; клиент не должен самостоятельно писать игровые HP/GM-права. Есть `SECURITY DEFINER` RPC с проверкой `auth.uid()` и членства/роли — **аудировать перед изменениями**; Supabase linter предупреждает о callable SECURITY DEFINER и о недоступной/выключенной защите от известных утечек паролей. Не утверждать, что эти предупреждения устранены. Скрытые ОЗ не должны утекать через прямые SELECT, журналы или API.

**Не менять базу «на глаз»**. Сначала запросить схему реальных таблиц/функций/политик, затем использовать миграции `apply_migration`; проверять RLS, grant/execute и соответствие UI. Не удалять чужих персонажей/комнаты/состояния ради теста. Тесты — изолированные и откатываемые.

## 6. Процедура безопасного редактирования

1. Сверить текущую ветку и затрагиваемые файлы. Таблицы/политики/RPC проверять, если меняется серверная часть. Не предполагать, что старое содержание чата совпадает с кодом.
2. Записать конкретный план изменений, зависимости фронтенд↔RPC↔БД, что не трогать. Сверить канон игровых механик.
3. Изменять минимальный набор файлов по одному с актуальным SHA; избегать параллельной записи в один путь. В SQL пользоваться миграциями, не сбрасывать production-таблицы.
4. Проверить синтаксис JS, используемые ID DOM, пути скриптов, имена RPC и поля таблиц. Не заменять сложную логику заглушкой.
5. Обновить версию и cache-busting `?v=...` для изменённых CSS/JS; дождаться успешного GitHub Pages Actions.
6. Тестировать в реальном браузере на телефоне/ПК и, если онлайн, **двумя отдельными аккаунтами на разных устройствах**. Проверить права (игрок не ГМ), видимость скрытых ОЗ, гибель/лечение, закрытие комнаты, синхронизацию, поведение при плохой связи. Успешная сборка ≠ полный end-to-end тест.
7. После работы обновить этот handoff и README, указать честно оставшиеся ограничения. Не копировать пароли, JWT, SMTP и service-role в GitHub/чат.

- Сначала проверить одинаковые размеры обложек на мобильном и ПК.

- Затем развивать полноценную тактическую карту (существa 1×1 / 2×2 / 3×1), серверную синхронизацию всех особенностей и листов, бестиарий и каталог предметов.
- Провести комплексное тестирование безопасности, лицензий, удаления персональных данных, восстановления пароля и конкурентных действий. На данный момент проект — онлайн-альфа, не готовый коммерческий продукт.
